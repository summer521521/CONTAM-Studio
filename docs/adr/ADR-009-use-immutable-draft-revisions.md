# ADR-009：使用不可变草稿Revision与确定性Zone UUID

## 状态

已接受。

## 背景

Phase 3B证明了哈希绑定的单字段Patch可以安全写入新副本，但每次批准都立即要求用户选择文件并切换项目，没有草稿历史、撤销或稳定对象身份。后续运行和结果若只依赖CONTAM编号，也无法可靠区分同一项目的不同修改状态。

## 决策

- 原始用户PRJ固定为只读Revision 0；Revision 1及以后是Rust在应用本地数据目录拥有的不可变快照。
- 每次批准的`Zone.volume_m3` Patch创建一个新Revision；已有快照不原地修改。
- Undo/Redo只验证并移动线性历史指针；Undo后新Patch截断Redo链。当前历史上限为32，不静默淘汰Revision。
- Zone身份由Rust使用固定命名空间UUID v5确定性生成，输入绑定原始基线SHA-256、Zone类型、基线CONTAM编号、基线源行号和名称。
- React使用`zone_id`提交编辑、结果与导出身份；CONTAM编号只用于显示及Rust/Python外部格式映射。
- 另存当前草稿只复制当前活动Revision到用户选择且不存在的新PRJ，不创建Revision、不自动切换项目、绝不覆盖原始文件。
- ContamX运行、SimRead结果和CSV导出必须绑定当前活动Revision；Revision变化时旧上下文失效。
- 草稿不跨应用重启恢复；崩溃残留不能自动恢复或信任。

## 理由

不可变字节快照使每个历史点可独立哈希、重读和运行，复用已经验证的单记号Patch边界而不需要完整PRJ序列化。确定性UUID让同一基线的对象在体积变化和历史切换中保持身份，同时通过基线SHA-256隔离不同项目内容。运行和结果绑定Revision可阻止旧manifest或图表跨草稿状态复用。

## 后果

- Rust新增`uuid 1.24.0`，只启用v5功能；许可证为Apache-2.0 OR MIT。前端和Python不新增UUID依赖。
- 内部草稿占用应用本地数据空间；正常切换和退出尽可能清理，但崩溃后可能残留不受信任文件。
- Revision 0依赖原始文件仍保持基线哈希；外部修改会阻止切回，但不会删除已有草稿。
- 当前只有线性历史和一个可修改字段；不支持多字段事务、多个Patch、复杂分支、多用户、跨重启恢复或AI修改。

## 替代方案

- **继续每次立即另存并切换项目**：无法提供撤销、草稿运行和稳定身份，拒绝。
- **在原始PRJ上原地写入并记录反向Patch**：可能破坏用户唯一资产，拒绝。
- **只用CONTAM编号或数组位置识别Zone**：不能满足跨Revision稳定映射和项目隔离，拒绝。
- **立即建立通用AST、数据库或Git式历史**：超出当前证据与单字段范围，拒绝。

## 待验证事项

- Windows安装包中的应用本地数据清理、磁盘配额和崩溃残留管理。
- 更复杂Zone布局和其他字段是否能够维持同等字节级前置条件。
- 多Patch事务、分支合并、长期项目身份与跨重启恢复。
- AI Patch在未来如何复用相同审批、Revision和审计边界。
